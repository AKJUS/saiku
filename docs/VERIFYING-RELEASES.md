# Verifying release artifacts

Every artifact `release.yml` publishes — the fat JAR, the dist zip, the
`ghcr.io/spiculedata/saiku` container image, and the npm packages — is
signed keylessly via [Sigstore](https://www.sigstore.dev/) and carries
[SLSA v1](https://slsa.dev/spec/v1.0/) build provenance, generated on
GitHub-hosted runners using GitHub's OIDC identity for the workflow run.
There's no private key to leak or rotate, and every signature is logged
to the public [Rekor](https://docs.sigstore.dev/logging/overview/)
transparency log.

This gets Saiku to roughly **SLSA Build L2**: provenance is generated by
a hosted build platform (GitHub Actions) and is non-forgeable (it's
signed by GitHub's own OIDC token, not something the build script could
fake). It does **not** get to L3 — that needs a hardened/isolated
builder (e.g. `slsa-framework/slsa-github-generator`) that can prove the
build steps themselves weren't tampered with, not just that the
workflow definition wasn't. That's a bigger lift and not attempted here.

Verifying is optional — Saiku works fine without it — but if you're
pulling a release into anything you care about, it costs one command.

## Fat JAR and dist zip

### Checksums

Every release ships a `SHA256SUMS` file alongside `saiku-<version>.jar`
and `saiku-dist-<version>.zip`. This only proves the download wasn't
corrupted or truncated — it says nothing about who produced the file —
but it's the fastest sanity check and needs no extra tooling:

```sh
curl -LO https://github.com/spiculedata/saiku/releases/download/v<version>/SHA256SUMS
curl -LO https://github.com/spiculedata/saiku/releases/download/v<version>/saiku-<version>.jar
sha256sum -c SHA256SUMS --ignore-missing
```

### Provenance (proves who built it)

Verify the SLSA provenance attestation with the
[GitHub CLI](https://cli.github.com/) (`gh`, v2.50+):

```sh
gh attestation verify saiku-<version>.jar --repo spiculedata/saiku
gh attestation verify saiku-dist-<version>.zip --repo spiculedata/saiku
```

A successful verify confirms the file's digest matches an attestation
that GitHub Actions produced from a run of `release.yml` in
`spiculedata/saiku`, signed via Sigstore's public-good instance. If the
file has been altered in any way since it was built — even one byte —
the digest won't match and verification fails.

## Container image

The image is both signed with `cosign` and carries a provenance
attestation, verifiable two ways.

### `gh attestation verify`

```sh
gh attestation verify oci://ghcr.io/spiculedata/saiku:<version> --repo spiculedata/saiku
```

### `cosign verify`

Install [`cosign`](https://docs.sigstore.dev/system_config/installation/),
then:

```sh
cosign verify \
  --certificate-identity-regexp '^https://github\.com/spiculedata/saiku/\.github/workflows/release\.yml@refs/tags/v.*$' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com \
  ghcr.io/spiculedata/saiku:<version>
```

`--certificate-identity-regexp` pins the check to signatures produced by
`release.yml` specifically (not just "anything signed under this GitHub
org") — a signature from a different workflow, or from anyone who isn't
GitHub Actions running in `spiculedata/saiku`, won't verify.

Both commands resolve the tag to its manifest-list digest before
checking, so `docker pull` after a successful verify is guaranteed to
fetch the exact content that was attested — not whatever the tag
happens to point at later.

## npm packages

`@concepttocloud/saiku-embed`, `@concepttocloud/saiku-embed-react` and
`@concepttocloud/saiku-design-system` all publish with
[`npm publish --provenance`](https://docs.npmjs.com/generating-provenance-statements),
which links the published tarball back to the exact GitHub Actions run
that built it. npm's registry verifies and displays this automatically
— look for the "Provenance" badge on the package page
(e.g. <https://www.npmjs.com/package/@concepttocloud/saiku-embed>).

To check locally, from a project that depends on the package:

```sh
npm audit signatures
```

This verifies registry signatures **and** provenance attestations for
every installed dependency that has them, and reports anything that's
missing or doesn't check out.

## If verification fails

Don't use the artifact. Open a security report per
[`SECURITY.md`](../SECURITY.md) rather than a public issue — a failed
verification could mean a corrupted mirror, but it could also mean a
compromised distribution channel.
